# Timeline Graph Language v1 — VyteMerge

## Estado

Draft v1

---

# 1. Purpose

This document evolves the Timeline concept beyond a rigid vertical line.

It exists because the first Timeline prototype was useful, but revealed an important limit:
a traditional vertical line with nodes still feels too close to a planner or agenda.

VyteMerge needs a language that feels more like:
- connected life
- movement through time
- nodes as meaningful moments
- convergences between actors/resources/places
- graph emergence without losing clarity
- mobile-friendly exploration

This document defines the next conceptual step:
# Timeline as graph-capable temporal path

---

# 2. Core shift

## From:
- straight line
- stacked events
- admin-like reading
- timeline as ordered list

## To:
- connected nodes
- temporal path
- movement
- local graph
- shared moments as hubs
- time as something you traverse

This is the key shift.

Timeline should still preserve:
- chronology
- next moments
- readability
- mobile usability

But it should stop feeling like:
- calendar clone
- event list
- pretty agenda

---

# 3. New core principle

## Timeline is not a line.
## Timeline is a path made of nodes.

The path may be:
- mostly linear
- slightly curved
- segmented
- branch-aware
- convergence-aware

But the important thing is:
the user should feel that time is **traversed**, not merely listed.

---

# 4. Primary visual unit

## Node

The node remains the main unit.

A node is:
- a temporal identity marker
- a destination
- a moment
- a hub
- a possible path decision point

The node may represent:
- a person
- a resource
- a place
- a shared event
- a slot
- a conflict
- a listing-backed temporal opportunity

Nodes are primary.
Connectors are secondary.

---

# 5. Connectors instead of dominant lines

Instead of one dominant line, use:
- subtle connectors
- path segments
- convergence indicators
- diverging connectors
- compressed gaps

The connector exists to answer:
- what connects to what
- what comes next
- where a path bends or merges

The connector should NOT dominate the visual reading.

---

# 6. Time should feel like movement

The user should feel:
- where "now" is
- what is next
- what is behind
- what is approaching
- what is colliding
- what is shared

This suggests a stronger role for:
- current position marker
- moving actor metaphor
- directional reading
- path progression

---

# 7. The actor as runner / traveler

A powerful metaphor for VyteMerge is:

## the actor is moving through their timeline

Not as a literal cartoon final UI,
but as a design principle.

This movement can be expressed by:
- current position marker
- directional micro-motion
- path progression
- visual sense of "approaching" a node
- visual "deviation" toward a shared event

This creates a more alive mental model than:
- “I have events on a line”

Instead:
- “I am moving through time”

---

# 8. Shared events as hubs

A shared event should not feel like:
- one more item in a list

It should feel like:
- a hub
- a convergence point
- a place where paths meet

Examples:
- football match
- medical appointment
- family brunch
- concert
- meeting room event

In a shared event:
- multiple actors may approach the same node
- a resource may also be part of that node
- the event becomes a local graph center

This is one of the most important visual differentiators for the product.

---

# 9. Slot vs event in graph language

## Slot
A slot is:
- possible time
- unoccupied opportunity
- a future opening
- a potential path branch

Graphically it should feel:
- lighter
- more open
- less committed
- less central

## Event
An event is:
- committed time
- occupied time
- connected time
- an actual destination on the path

Graphically it should feel:
- stronger
- more identity-rich
- more central
- more gravitational

---

# 10. Sparse path vs dense cluster

## Sparse path
If the user has very few events:
- do not show long dead lines
- show meaningful path points
- compress the emptiness
- preserve sequence, not literal distance

The experience should feel like:
- next important stops on my path

## Dense cluster
If many things happen nearby:
- show a richer local cluster
- make path relationships more visible
- emphasize local density, not just list stacking

The experience should feel like:
- this area of my life is active and connected

---

# 11. Home vs Timeline in this new model

## Home
Home should probably contain the **primary mini-timeline expression**.

This can work like:
- stories rail
- mini path
- compact graph strip
- horizontal sequence
- small set of next connected moments

Home becomes:
# my line + what connects to it

This is likely the right place for:
- immediate time
- compact motion
- simple connected life glance

## Timeline page
Timeline page becomes the expanded view:
- more depth
- more branching
- more connection
- more conflict
- more context

This page should not simply repeat Home vertically.
It should deepen the idea.

---

# 12. Mobile-friendly implications

Mobile-friendly does NOT require:
- a long vertical list
- a rigid single-axis layout
- stacked administrative reading

Mobile-friendly MAY be:
- horizontal rails
- snap-based node sequences
- vertically scrolling path sections
- graph-lite clusters
- one-path-at-a-time progression
- compact shared hubs
- expandable local complexity

The key is:
- readability
- touchability
- no overload
- progressive reveal

---

# 13. Possible visual models to explore

## Model A — Organic vertical path
A softer vertical path:
- less rigid
- small bends
- nodes feel like stops
- shared moments become side convergences

### Good for
- easy migration from current prototype
- keeping chronology strong

### Risk
- still feels too list-like if overdone

---

## Model B — Home as stories-like time rail
A compact horizontal rail on Home:
- next moments
- nodes as temporal identity markers
- swipe/scroll through immediate future
- one or two connected opportunities inserted naturally

### Good for
- immediate user understanding
- mobile
- making Home feel alive

### Risk
- can become too social-feed-like if not temporal enough

---

## Model C — Graph-lite expanded timeline
The Timeline page becomes:
- path-centric
- locally branching
- shared events as hubs
- conflicts as collision zones
- resources as visible connected nodes

### Good for
- making the product feel unique
- showing "everything connects"

### Risk
- can become too complex too quickly if not tightly controlled

---

# 14. Recommended next design exploration

The next prototype step should NOT be:
- more polishing of the rigid vertical line

It should be:
# exploration of 3 visual directions

## Direction 1
Personal path — clean, node-first, minimal connectors

## Direction 2
Home mini-timeline — stories/rail/path hybrid

## Direction 3
Expanded graph-lite timeline — shared hubs and conflict points

These should be explored as visual variants before deciding what becomes canonical.

---

# 15. Rules for this next exploration

## Rule 1
Do not overbuild architecture yet.

## Rule 2
Prototype pages and visual systems first.

## Rule 3
Keep the focus on:
- node language
- connector language
- movement
- shared hubs
- conflicts
- home mini-timeline

## Rule 4
Do not let graph exploration destroy readability.

## Rule 5
Preserve the user's sense of:
- now
- next
- shared
- conflict
- path

---

# 16. What should remain true no matter the visual model

Regardless of final shape, Timeline must preserve:

- time has direction
- nodes are the main unit
- slot and event are clearly different
- shared events feel shared
- conflicts feel meaningful
- private timelines can intersect without full exposure
- resources can behave like temporal entities
- the product still feels mobile-friendly
- Timeline remains more alive than a planner and more useful than an abstract graph

---

# 17. Design questions this document opens

These are the questions the next visual exploration should answer:

1. How visible should connectors be?
2. How literal should the "runner" or current-position metaphor be?
3. Should Home own the strongest mini-timeline?
4. How much of the graph should appear on the Timeline page by default?
5. How do shared hubs appear without clutter?
6. How do we show movement without becoming gimmicky?
7. How do we preserve mobile simplicity while allowing graph richness?

---

# 18. Closing principle

> **VyteMerge Timeline should evolve from a rigid line into a graph-capable temporal path where users feel themselves moving through connected moments, not merely reading a list of events.**
