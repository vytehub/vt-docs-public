# Catalog (Overview)

## TL;DR
El módulo **Catalog** define el **"qué"** en VyteMerge: las definiciones reusables que un Profile ofrece.

- **Service** = definición operativa de un servicio (duración, precio base, buffers, form, policy)
- **Product** = definición de un producto vendible (nombre, descripción, media, tags)

El Catalog **no vende ni agenda** por sí solo.
Para vender o reservar se usa un **Listing**, que define el **"cómo se ofrece"**
(copy, media, tags, canales, promociones, modificadores de precio).

> **Service = dominio operativo. Listing = dominio comercial/discovery.**

---

## Contexto / Objetivo

En la vida real, el mismo "qué" puede venderse en múltiples variantes:

### Ejemplos
**Service: "Masaje"**
- estándar 60 min → Listing con precio base
- "Masaje express" → Listing con ajuste de duración
- promo "2x1" → Listing con modificador de precio
- "a domicilio" → Listing con place alternativo (futuro)

**Product: "Shampoo"**
- venta individual → Listing regular
- pack x3 → Listing con modificador de bundle
- promo por canal → Listing canal VIP

Si mezclamos definición + venta + agenda en un mismo objeto, terminamos con:
- duplicación de información (mismo servicio repetido múltiples veces)
- dificultad para actualizar (cambiar precio/duración en varios lugares)
- inconsistencias (copy/media mezclado con reglas operativas)

**Catalog existe para separar lo estable (definición operativa) de lo variable (presentación comercial).**

## Qué incluye el módulo Catalog

### 1) Services
Un **Service** representa la definición operativa reusable de un servicio.

Incluye:
- `name`, `description`
- `durationMin` (duración base — fuente de verdad)
- `basePrice` (precio base — fuente de verdad)
- `preBufferMin`, `postBufferMin` (buffers operativos)
- `intakeForm` (datos requeridos al cliente)
- `confirmationPolicy` (política de confirmación)
- `location` (lugar operativo de referencia)
- `tags` (taxonomía global curada + custom limitado)

**Service NO almacena media.** Las fotos/videos pertenecen al Listing.
Ver decisión completa en `02.services.md`.

**Importante:**
- `basePrice` en Service es la fuente de verdad del precio.
- El Listing puede aplicar modificadores (`EffectivePrice = basePrice + modifiers`).
- Listing NO sobrescribe el precio base; solo aplica deltas.

---

### 2) Products
Un **Product** representa un bien vendible (físico o digital).

Incluye típicamente:
- `name`, `description`
- `category`, `tags`
- `baseMedia` (fotos, cover — fallback si Listing no tiene media propia)
- (futuro) variantes, stock, logística

> Nota: Product mantiene `baseMedia` como fallback. Service no almacena media.
> Esta diferencia es intencional: Product es un objeto de catálogo visual;
> Service es una definición operativa.

---

### 3) Catálogo del Profile
Cada Profile tiene un catálogo compuesto por:
- Services (con sus reglas operativas)
- Products

Esto habilita:
- organización interna del vendedor
- reutilización en múltiples Listings
- analytics por ítem del catálogo (demanda real, conversiones)

---

## Qué NO hace Catalog (límites claros)
Catalog **NO** define:

- media / fotos / videos de presentación (van en Listing — aplica a Services; Products mantienen media base como fallback)
- copy de marketing / título promo / descripción de oferta (van en Listing)
- modificadores de precio, descuentos, promos, bundles (van en Listing)
- visibilidad y distribución: public / followers / channels / partners (van en Listing/Channels)
- scheduling, slots, disponibilidad proyectada (van en Timeline + Conflict Rules)
- bookings / reservas (van en Booking)
- orders / compras (van en Order)

## Relación con Listings

```
Service ──(1:N)──▶ Listing (Service Listing) ──▶ Booking
Product ──(1:N)──▶ Listing (Product Listing) ──▶ Order
```

Un Listing siempre referencia un origen del catálogo:
- **Service Listing** → referencia `ServiceId`
- **Product Listing** → referencia `ProductId`

El Listing:
- hereda `basePrice` del Service (y aplica modificadores opcionales)
- define copy propio (título, descripción de la oferta)
- define media propia (fotos/videos de la oferta)
- define tags de discovery, categoría, canales, promos

> **Catalog = definición estable**
> **Listing = oferta comercial concreta**

---

## Service Lifecycle

```
[Draft] ──▶ [Active] ──▶ [Archived]
```

- **Draft**: configuración incompleta. No genera Slots.
- **Active**: operativo. Puede generar Slots y aceptar Bookings.
- **Archived**: discontinuado. Solo histórico. No admite nuevos Listings.

---

## Integración con otros módulos

### Listings
- toma un Service/Product como base
- define "cómo se vende" (copy, media, canales, promos, modificadores de precio)
- es lo que aparece en feed/marketplace/campaigns

### Timelines + Conflict Rules + Places
En servicios reservables:
- Timeline define el tiempo disponible
- Conflict Rules determinan qué bloquea disponibilidad
- Places definen "dónde" y zona horaria

### Bookings / Orders
- Booking = reserva de tiempo (Service Listing) — guarda snapshot de precio final
- Order = compra de ítems (Product Listing)

---

## Reglas prácticas (MVP)
- Un Service/Product puede existir sin Listings (todavía no se vende)
- Un Listing siempre referencia un Service/Product (no hay Listing "huérfano")
- Service no almacena media; Listing es dueño de la media
- Cambiar un Service/Product no afecta Bookings/Orders pasados
  (los Bookings guardan snapshot de precio y términos)
