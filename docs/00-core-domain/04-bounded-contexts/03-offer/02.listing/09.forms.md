# Forms (en Listings)

## TL;DR
Un **Listing** puede requerir un **Form** para capturar información necesaria antes de confirmar un Booking (o completar una compra).

- El Listing **no define** el formulario: solo lo **referencia**.
- El Booking guarda un **snapshot** de la versión y las respuestas.
- Esto permite que Forms evolucione (encuestas, fichas de clientes) sin complicar Listings.

---

## Para qué sirve en Listings
Cuando alguien reserva/comprar, hay datos que el proveedor necesita para:
- prestar el servicio correctamente
- coordinar logística
- cumplir requisitos (salud, edad, restricciones)
- reducir idas y vueltas por chat

Ejemplos:
- Cumpleaños: acompañantes, alergias, confirmación
- Veterinaria: especie, peso, síntomas
- Estética: preferencias, observaciones
- Partido: posición, nivel, confirmación

---

## Qué declara el Listing (integración mínima)
A nivel conceptual, el Listing declara:

- `FormId` (opcional): referencia a un Form template
- `FormRequired` (bool): si es obligatorio completarlo
- `FormTiming` (opcional): cuándo se completa  
  - recomendado MVP: `BeforeConfirm` (antes de confirmar)

> MVP sugerido: solo `FormId` + `FormRequired`, y siempre “antes de confirmar”.

---

## Datos base (Intake mínimo)
Incluso sin un Form personalizado, un Booking normalmente necesita:
- `Name`
- `LastName`
- `Email`

Regla práctica:
- si el usuario está logueado, estos campos se autocompletan
- si no está logueado, se piden como parte del flujo

Luego el Form puede agregar campos adicionales:
- `Phone`
- “¿Viene con acompañante?”
- “¿Es celíaco?”
- “Observaciones”

---

## Snapshot en Booking (regla clave)
Los forms cambian con el tiempo (se agregan preguntas, se ajustan opciones).
Para que un booking pasado no se “rompa”:

Cuando un booking usa un form, se guarda:
- `FormId`
- `FormVersion` (o `PublishedAt`)
- `SubmissionId` (respuesta)
- (opcional) snapshot de preguntas relevantes

Esto permite:
- auditoría y trazabilidad
- consistencia histórica aunque el owner edite el form después

---

## Privacidad (en contexto de Listings)
Las respuestas pueden ser sensibles.

Reglas recomendadas:
- solo el owner y operadores autorizados ven las submissions del booking
- el usuario que respondió puede ver su propia submission
- nunca se publican respuestas en feed salvo un caso explícito de “encuesta”

---

## Evolución futura (sin cambiar Listings)
El mismo Form puede reutilizarse fuera de Listings:
- encuestas independientes (en Channels post-v1, ver [ADR-0007](../../../../private/decisions/ADR-0007-channels-deferred-from-v1.md))
- ficha de clientes (historial) para profesionales
- integraciones externas (export/import)

Como Listings solo referencia `FormId`, la evolución ocurre en Forms sin inflar este módulo.

---

## Checklist (MVP)
- [ ] Listing puede tener `FormId` opcional
- [ ] Si `FormRequired=true`, bloquear confirmación hasta completar
- [ ] Booking guarda snapshot: `FormId + Version + SubmissionId`
- [ ] Respuestas visibles solo a actores permitidos (Access/Agreements)
